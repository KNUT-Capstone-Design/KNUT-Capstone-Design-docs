- **버전:** Draft v0.1
- **작성일:** 2026-10-12
- **상태:** 팀 검토용 초안
- **적용 범위:** MVP 기능, 통합 및 배포 검증
- **관련 문서:** [기능 명세](01_Feature_Specification.md), [사용자 흐름](02_User_Flow.md), [시스템 아키텍처](03_System_Architecture.md), [DB 설계](04_Database_Design.md), [API 명세](05_API_Specification.md), [UI 설계](06_UI_Design.md)

## 1. 목적

본 문서는 URL·문자·QR 검사, 결과 안내, 예방 교육과 퀴즈로 구성된 MVP의 테스트 범위·방법·환경·담당자·완료 기준을 정의한다. 기능 실행 여부뿐 아니라 탐지 결과의 일관성, 개인정보 보호, 장애 복구와 실제 배포 환경의 시연 가능성을 함께 검증한다.

테스트 결과는 서비스가 악성 여부를 확정하거나 안전을 보증한다는 의미가 아니다. 탐지 성능은 정의된 평가 데이터와 규칙 버전을 기준으로 측정하고 알려진 한계와 함께 기록한다.

## 2. 테스트 목표

1. URL·문자·QR 검사가 명세의 입력과 결과 계약대로 동작하는지 확인한다.
2. 위험 등급·점수·근거·권장 행동이 같은 규칙 버전에서 일관되게 계산되는지 확인한다.
3. 입력 오류, 분석 실패, DB 장애와 네트워크 오류에서 사용자가 복구할 수 있는지 확인한다.
4. 검사 원문, 전체 URL과 QR 이미지가 DB·로그·브라우저 영구 저장소에 남지 않는지 확인한다.
5. 교육·퀴즈 데이터가 PostgreSQL을 통해 정확하게 조회·채점되는지 확인한다.
6. 모바일·데스크톱과 키보드 환경에서 핵심 사용자 흐름을 완료할 수 있는지 확인한다.
7. OCI 배포 환경에서 FE·BE·PostgreSQL 통합 흐름과 장애 복구를 검증한다.
8. 정상·위험 평가 데이터로 탐지율, 오탐률, 근거 표시율과 처리 시간을 측정한다.

## 3. 테스트 범위

### 3.1 필수 범위

- F-001~F-004 기본 웹사이트와 공통 입력·결과
- F-101 URL 위험도 분석
- F-102 문자 메시지 분석
- F-103 QR 코드 분석
- F-201~F-203 예방 교육과 퀴즈
- NFR-001~NFR-004 보안, 안정성, 접근성과 결과 신뢰성
- API v1 요청·응답·오류 계약
- PostgreSQL 마이그레이션, seed, 조회, 채점, 백업과 복구
- 실제 FE 배포 환경과 OCI BE·DB의 통합

### 3.2 제외 범위

- 회원가입·로그인과 개인 기록
- 기관 구성원·교육 배정·익명 통계
- 관리자 화면
- 문자·웹페이지 캡처 OCR
- 가짜 로그인 페이지 동적 분석
- 조작 이미지 판별
- 실제 결제·과금·청구
- 자체 AI 모델 학습

제외 기능은 2차 개발 착수 시 별도 테스트 범위와 개인정보 기준을 추가한다. MVP 테스트에 포함된 것처럼 결과를 보고하지 않는다.

## 4. 테스트 원칙

- 기능 명세의 완료 조건과 API 명세를 예상 결과의 기준으로 사용한다.
- 자동 테스트와 수동 테스트를 함께 사용하며 핵심 계산·계약·회귀 항목은 자동화한다.
- 정상값, 경계값, 오류값과 장애 상황을 모두 확인한다.
- FE와 BE는 동일한 fixture와 예제 응답을 사용한다.
- 실제 악성 사이트를 열거나 파일을 실행하지 않는다.
- 실제 개인정보, 활성 인증정보와 운영 비밀값을 테스트 데이터로 사용하지 않는다.
- 같은 입력과 규칙 버전은 같은 점수·등급·근거를 반환해야 한다.
- 결함 수정 후 해당 케이스와 관련 회귀 케이스를 다시 실행한다.
- P0 항목은 구현 담당자 외 다른 팀원이 교차 검증한다.

## 5. 테스트 단계

### 5.1 단위 테스트

URL 정규화·검증, 문자 URL 추출, 탐지 규칙, 위험 점수 계산, QR 디코딩 결과 처리, 퀴즈 채점과 입력 모델을 검증한다. 외부 평판 서비스와 DB는 필요한 경우 대역을 사용한다.

### 5.2 API·DB 통합 테스트

FastAPI 테스트 클라이언트와 테스트용 PostgreSQL을 사용해 요청·응답, 마이그레이션, seed, 조회, 채점, 오류 변환과 트랜잭션을 확인한다. 테스트 DB는 운영 DB와 분리한다.

### 5.3 Frontend 테스트

입력 검증, 로딩·빈 상태·오류·부분 결과, 결과 분기와 접근성을 검증한다. API 성공·실패·시간 초과 응답을 재현하고 입력 유지와 재시도를 확인한다.

### 5.4 E2E 테스트

브라우저에서 메인 → 검사 → 결과 → 교육 또는 퀴즈의 전체 흐름을 실행한다. 네트워크 요청 횟수, 직접 경로 접근, 뒤로가기와 새로고침도 확인한다.

### 5.5 탐지 성능 평가

버전이 고정된 평가 데이터셋을 일괄 분석하고 정답 라벨과 비교한다. 기능 테스트와 분리해 결과를 집계하며 규칙 변경 전후 수치를 보존한다.

### 5.6 배포 인수 테스트

실제 FE·OCI BE·PostgreSQL 환경에서 HTTPS, CORS, 컨테이너 재시작, DB 장애, 백업 복원과 핵심 시연 흐름을 검증한다.

## 6. 테스트 환경

| 환경 | 목적 | 주요 구성 | 데이터 |
|---|---|---|---|
| Local | 단위·컴포넌트 개발 | 개발 PC, FE·BE 로컬 실행 | 고정 fixture, 테스트 DB |
| Integration | API·DB·E2E 통합 | FE·BE 개발 환경, Docker PostgreSQL | seed와 합성 평가 데이터 |
| Production-like | 배포 인수 | 실제 FE 배포, OCI Docker BE·PostgreSQL, HTTPS | 개인정보 없는 인수 데이터 |

초기 브라우저 범위는 최신 안정 버전 Chrome·Edge·Safari와 모바일 Chrome·Safari로 한다. 실기기 확보가 어렵다면 확인한 환경과 미검증 환경을 결과에 구분해 기록한다.

반응형 검증 기준은 모바일 360px, 태블릿 768px, 데스크톱 1024px 이상이며 200% 확대와 키보드 전용 사용을 포함한다.

- **P2:** 편의성이나 발생 가능성이 낮은 예외 상황에 영향을 준다.

## 8. 테스트 케이스 작성 형식

각 케이스는 다음 항목을 사용한다.

```text
테스트 ID:
제목:
관련 기능·API:
우선순위:
테스트 단계:
사전 조건:
입력 또는 데이터:
실행 절차:
예상 결과:
실제 결과:
결과: Not Run / Pass / Fail / Blocked
담당자:
증거 또는 이슈:
```

### URL-001 정상 HTTPS URL 분석 예시

- **관련 기능·API:** F-101, `POST /api/v1/analysis/url`
- **우선순위:** P0
- **테스트 단계:** API, E2E
- **사전 조건:** FE·BE가 정상 실행되고 규칙 버전이 고정되어 있다.
- **입력:** 테스트용 정상 HTTPS URL
- **절차:** URL 검사 화면에 입력하고 검사 버튼을 한 번 누른다.
- **예상 결과:** 요청이 한 번 전송되고 공통 결과에 등급·점수·판정 요약·근거·권장 행동·분석 버전이 표시된다. 입력 URL은 DB와 로그에 저장되지 않는다.

## 10. API 계약 테스트

- 모든 성공·오류 응답에 동일한 UUID `request_id`와 `X-Request-ID`가 있는지 확인한다.
- 분석·오류·교육·퀴즈 응답에 `Cache-Control: no-store`가 적용되는지 확인한다.
- 필수 필드 누락·타입 오류·정의하지 않은 필드는 `422 VALIDATION_ERROR`인지 확인한다.
- 잘못된 JSON은 원문을 노출하지 않는 `400 INVALID_JSON`인지 확인한다.
- 오류 응답이 공통 구조이며 서버 경로·비밀값·전체 입력을 포함하지 않는지 확인한다.
- BE 15초, FE 30초의 초기 시간 제한과 시간 초과 복구를 배포 환경에서 확인한다.
- 분석 API 60초 20회, 교육·퀴즈 합산 60초 60회의 초기 제한과 `429`, `Retry-After`를 확인한다.
- 허용한 FE 출처만 CORS 접근이 가능하고 필요한 헤더가 노출되는지 확인한다.
- OpenAPI 스키마, FE 타입과 Markdown 명세의 필드·enum·null 가능성을 비교한다.

## 14. 탐지 성능 평가

### 14.1 평가 데이터셋 초안

| 구분 | 목표 수량 | 주요 유형 |
|---|---:|---|
| 정상 URL | 50 | 일반 사이트, 긴 경로, 쿼리, IDN, HTTP·HTTPS |
| 위험 URL | 50 | 유사 도메인, IP 주소, 설치·인증정보 유도 |
| 정상 문자 | 30 | 택배·로그인·앱 안내를 포함한 정상 문맥 |
| 스미싱 문자 | 50 | 택배, 부고, 기관, 금융, 투자, 지인, APK |
| 정상 URL QR | 20 | 다양한 크기·여백·명암 |
| 위험 URL QR | 20 | 위험 URL 문자열을 담은 합성 QR |
| 기타 QR | 20 | 일반 텍스트, 손상, 복수, 미인식 |

총 240개를 초기 목표로 하되 중복 변형만으로 수량을 채우지 않는다. 공개 사례는 출처와 수집일을 기록하고 개인정보를 제거한다. 위험 URL은 접속하지 않고 비활성 문자열이나 팀의 안전한 테스트 도메인으로 대체한다.

### 14.2 라벨 기준

각 데이터에는 데이터 ID, 유형, 기대 분류, 기대 등급, 필수 근거, 적용 예상 규칙, 출처, 작성자와 검토자를 기록한다. 탐지 담당자가 1차 라벨을 작성하고 PM 또는 다른 팀원이 교차 검토한다. 의견이 다르면 근거와 최종 결정을 남긴다.

### 14.3 지표

- 위험 탐지율 = 위험 데이터를 주의 또는 위험으로 분류한 수 / 전체 위험 데이터 수
- 위험 등급 재현율 = 위험 데이터를 위험으로 분류한 수 / 전체 위험 데이터 수
- 정상 오탐률 = 정상 데이터를 주의 또는 위험으로 분류한 수 / 전체 정상 데이터 수
- 등급 일치율 = 기대 등급과 실제 등급이 같은 수 / 등급 평가 대상 수
- 필수 근거 표시율 = 기대 근거를 모두 표시한 수 / 근거 평가 대상 수
- QR 인식 성공률 = 판독 가능한 QR을 정확히 추출한 수 / 판독 가능한 QR 수
- URL·문자·QR별 평균과 95백분위 분석 시간

정확도 목표치는 1차 베이스라인 측정 후 팀에서 확정한다. 평가 데이터에 맞춘 과적합을 줄이기 위해 튜닝용 데이터와 최종 평가용 데이터를 분리한다. 규칙 변경 시 규칙 버전, 데이터셋 버전, 이전·이후 지표와 새 오탐·미탐을 기록한다.

## 15. 성능·안정성 테스트

- 대표 정상 입력으로 URL·문자·QR별 평균과 95백분위 응답 시간을 측정한다.
- FE가 30초 후 요청을 중단하고 입력 유지·재시도를 제공하는지 확인한다.
- BE가 분석을 15초 이내에 종료하거나 시간 초과 오류로 정리하는지 확인한다.
- 큰 이미지, 긴 문자와 URL 5개 문자에서 메모리·CPU와 프로세스 안정성을 확인한다.
- 외부 평판 전체·일부 실패와 지연에서도 내부 분석 결과가 유지되는지 확인한다.
- 동시 요청에서 데이터가 섞이지 않고 요청 ID가 분리되는지 확인한다.
- 동시 사용자 수와 성능 통과 수치는 OCI 자원을 확인한 뒤 확정한다.

## 17. 결함 등급과 처리

### Critical

- 위험 입력을 근거 없이 안전하다고 보장함
- 검사 원문·개인정보·비밀값 유출
- 의심 URL 또는 파일 자동 실행
- 서비스 전체 사용 불가
- 운영 데이터 손실

### High

- URL·문자·QR 중 핵심 검사 하나가 동작하지 않음
- 위험 점수·등급·치명 규칙 계산 오류
- QR 임시 파일 미삭제
- 교육·퀴즈 주요 흐름 또는 채점 오류

### Medium

- 일부 오류에서 입력 유지·재시도가 불가능함
- 지원 브라우저나 화면 크기에서 핵심 사용이 어려움
- 교육 필터·추천 또는 접근성의 주요 문제

### Low

- 오탈자, 간격, 정렬 등 핵심 사용에 영향이 적은 문제

결함은 재현 절차, 기대·실제 결과, 환경, 요청 ID, 개인정보를 제거한 증거와 관련 테스트 ID를 GitHub Issue에 기록한다. 수정 PR은 해당 테스트와 회귀 테스트 결과를 연결한다.

- 모바일 360px, 데스크톱과 키보드 핵심 흐름이 통과한다.
- OCI 배포 환경의 전체 시연 흐름이 3회 연속 성공한다.
- 탐지 성능 측정 결과, 데이터셋·규칙 버전과 알려진 한계가 기록되어 있다.

Medium 결함은 핵심 흐름과 개인정보에 영향을 주지 않고 수정 일정과 우회 방법이 합의된 경우에만 남길 수 있다. Low 결함은 목록과 후속 처리 계획을 남긴다.

## 21. 결과 기록

자동 테스트는 PR 또는 CI 결과를 증거로 남기고 수동·배포 테스트는 다음 형식으로 기록한다.

| 테스트 ID | 환경 | 실행일 | 담당자 | 결과 | 증거·이슈 |
|---|---|---|---|---|---|
| URL-001 | Integration | YYYY-MM-DD | 이름 | Not Run | 링크 |

결과 값은 `Not Run`, `Pass`, `Fail`, `Blocked`만 사용한다. `Blocked`는 원인과 해제 조건을 반드시 기록한다. 스크린샷·로그에는 원문 URL, 문자, QR 추출값과 비밀값이 포함되지 않도록 검토한다.

최종 발표용 결과에는 환경별 실행 건수, 결함 현황, 탐지 성능, 개인정보·복구 검증, 지원·미검증 환경과 알려진 한계를 요약한다.

- **최초 작성 / 마지막 검토:** 2026-11-18
- **상태:** 검토 사항 등록 · 기준 문서 반영 전
- **목적:** 구현 과정에서 발견한 문서 누락, 설계와 코드의 차이, 추가 결정 사항을 지속적으로 관리한다.
- **기준 문서:** 01~07 v1.0, 문서 저장소 커밋 `45d97fb`
- **이번 검토 범위:** 로컬 백엔드의 라우터, 스키마, 인증·권한, 모델, 마이그레이션, 배포 설정, 테스트 코드 및 README

> 이 파일은 변경 요청과 검토 이력을 관리하는 문서다. 등록된 제안은 확정 명세가 아니며, 코드에 존재한다는 이유만으로 MVP 범위를 변경하지 않는다. 주제별 최종 기준은 [문서 안내](../README.md)에 따른다.

## 1. 관리 방법

- 항목 ID는 `GAP-001`부터 순차 부여하고 완료 후에도 삭제하거나 다시 번호를 붙이지 않는다.
- 유형은 **문서 누락**, **문서·구현 불일치**, **설계 대비 미구현**, **추가 결정 필요**로 구분한다.
- 상태는 **미반영 → 결정 필요 / 반영 중 → 반영 완료**로 관리한다. 보류할 때는 사유와 재검토 조건을 남긴다.
- 우선순위는 P0(범위·연동·운영 전 선결), P1(관련 기능 완료 전 필요), P2(정리·추적 개선)로 구분한다. 보안 취약점의 확정 심각도 등급은 아니다.
- 완료 시 결정 내용, 수정 문서, 관련 코드 커밋·PR, 필요한 검증 결과를 남긴다. 이 파일에 내용을 적은 것만으로 완료 처리하지 않는다.
- PM/Docs는 기준 문서를 반영하고, BE·FE 담당자는 계약 및 구현 영향을 확인한다. 담당 제안은 작업 배정이 확정됐다는 뜻이 아니다.

### 검토의 한계

이번 확인 당시 BE는 `main`에 커밋이 없고 구현 파일이 모두 미추적 상태였다. 따라서 아래 내용은 **2026-11-18 로컬 작업 트리** 기준이며 배포 상태나 원격 저장소의 구현을 뜻하지 않는다. 테스트 코드는 읽었지만 실행하지 않았다. 테스트 통과, PostgreSQL 실동작, OCI 배포 완료를 확인한 것은 아니다.

아래 BE 상대 링크는 문서 저장소와 BE 저장소가 같은 workspace에 있는 로컬 구조를 기준으로 한다. GitHub에서 다른 저장소의 코드로 자동 연결되지 않으므로, BE 커밋 후 해당 커밋의 링크를 추가한다.

## 2. 현재 상황 요약

- 코드에는 회원가입, 일반·서비스 관리자 로그인, 토큰 갱신, 로그아웃, 내 정보 조회와 DB 연결 상태 확인이 있다.
- 기존 문서는 회원·관리자 인증을 2차 범위로 분리한다. 인증 기반을 먼저 개발한 것인지, 출시 범위를 바꾼 것인지 결정 기록이 필요하다.
- 등록된 업무 라우터는 인증과 health뿐이다. URL·문자·QR 분석 및 교육·퀴즈는 현재 확인한 코드에 없다.
- 첫 마이그레이션은 교육 테이블이 아니라 `users`, `refresh_sessions`를 만든다.
- 응답 구조, 요청 ID, health 의미, DB 계정 권한 등에서 기준 문서와 차이가 있다.

### GAP-002 인증 API 상세 계약 추가

- **유형 / 우선순위 / 상태:** 문서 누락 / P0 / 미반영
- **근거:** [인증 라우터](../../KNUT-Capstone-Design-BE/app/api/routes/auth.py), [인증 스키마](../../KNUT-Capstone-Design-BE/app/schemas/auth.py), [권한 의존성](../../KNUT-Capstone-Design-BE/app/api/dependencies.py)
- **현재 구현:** 아래 경로는 모두 `/api/v1`을 앞에 붙인다.
  - `POST /auth/signup`: 이메일·비밀번호로 가입, 201, 일반 사용자로 자동 로그인. 중복 이메일 409.
  - `POST /auth/login`: 일반 로그인, 200.
  - `POST /auth/admin/login`: 서비스 관리자 로그인, 200. 일반 계정은 401.
  - `POST /auth/refresh`: refresh 쿠키를 사용해 세션 교체 및 access token 재발급, 200. 유효하지 않으면 401.
  - `POST /auth/logout`: 현재 refresh 세션 폐기 및 쿠키 삭제, 200. 쿠키가 없어도 성공 응답.
  - `GET /auth/me`: Bearer access token으로 활성 사용자 조회, 200. 인증 실패 401.
  - `GET /auth/admin/me`: 관리자 정보 조회, 200. 일반 사용자 403.
- **입력 규칙:** 이메일 소문자 정규화. 가입 비밀번호 10~128자, 문자와 숫자 각각 포함, 공백만 있는 값 금지. `isalpha()`·`isdigit()` 기준이므로 영문·ASCII 숫자만 허용하는 정책과는 다르다. 가입·로그인 추가 필드는 거부한다.
- **응답:** 인증 성공은 `access_token`, `token_type`, `expires_in`, `user`; 사용자 정보는 `id`, `email`, `role`, `status`, `created_at`, `last_login_at`; 로그아웃은 `message`다. 비밀번호 해시는 응답하지 않는다.
- **추가할 내용:** 요청·응답 예제, 쿠키, 401/403/409/422/429 오류 코드와 FE 처리, 가입 직후 자동 로그인 흐름. 비밀번호 변경·재설정, 이메일 인증, 탈퇴는 현재 미구현으로 구분한다.
- **반영 대상:** 01 F-310~F-311, 02 회원 흐름, 05 인증 계약, 06 인증 화면, 07 인증 테스트

### GAP-003 토큰 수명·로그아웃·브라우저 연동 정책

- **유형 / 우선순위 / 상태:** 문서 누락·추가 결정 필요 / P0 / 결정 필요
- **근거:** [보안 함수](../../KNUT-Capstone-Design-BE/app/core/security.py), [설정](../../KNUT-Capstone-Design-BE/app/core/config.py), 인증 라우터, 앱 CORS 설정
- **현재 구현:** JWT access token은 HS256, 기본 15분. refresh token은 난수 문자열이고 DB에는 SHA-256 해시만 저장한다. 기본 수명은 14일이며 갱신할 때 기존 세션을 폐기하고 새 세션을 만든다.
- **쿠키:** 이름 `refresh_token`, HttpOnly, SameSite=Lax, Path=`/api/v1/auth`, Secure는 환경설정에 따른다. Domain은 지정하지 않는다. CORS는 허용 origin 목록과 credentials를 사용한다.
- **주의할 동작:** 로그아웃은 refresh 세션을 폐기한다. 이미 발급한 access JWT를 즉시 폐기하는 구조는 아니므로, 계정 상태 변경 등 별도 조건이 없다면 만료까지 사용할 수 있다. 갱신 시에도 `last_login_at`이 변경된다.
- **추가 결정:** FE 토큰 보관 위치, 새로고침 복구, credentials 옵션, 동시 갱신 처리, 만료 후 재로그인, 단일 기기/전체 기기 로그아웃, 절대 세션 수명, `last_login_at`의 의미를 정한다.
- **배포 확인:** 서로 다른 origin과 서로 다른 site를 구분한다. 실제 FE·BE 도메인 조합에서 SameSite=Lax 쿠키가 전송되는지 검증한다. HttpOnly나 CORS 설정만으로 CSRF 방어 완료라고 판정하지 않는다.
- **검증 필요:** 동일 refresh token의 순차 재사용과 동시 요청을 시험한다. 현재 조회 후 폐기하는 흐름에는 행 잠금이나 조건부 갱신이 없어 동시성 보장이 확인되지 않았다. 취약점 재현 완료를 뜻하지 않는다.
- **반영 대상:** 02, 03 보안·배포, 05 인증, 06 세션 UI, 07 보안·E2E

### GAP-004 회원·세션 테이블과 개인정보 수명 추가

- **유형 / 우선순위 / 상태:** 문서·구현 불일치 / P0 / 결정 필요
- **문서 기준:** 04는 MVP에 회원 테이블을 만들지 않으며 교육·퀴즈 데이터만 저장하도록 한다.
- **근거:** [User](../../KNUT-Capstone-Design-BE/app/models/user.py), [RefreshSession](../../KNUT-Capstone-Design-BE/app/models/refresh_session.py), [첫 마이그레이션](../../KNUT-Capstone-Design-BE/alembic/versions/20261118_01_create_auth_tables.py)
- **현재 구현:**
  - `users`: UUID PK, 유일 이메일, 비밀번호 해시, 역할, 계정 상태, 생성·수정·최근 로그인 시각.
  - `refresh_sessions`: UUID PK, 사용자 FK, 유일 토큰 해시, 생성·만료·폐기 시각. 사용자 삭제에 CASCADE.
  - API 역할·상태 값은 `user/admin`, `active/disabled`; SQLAlchemy enum의 DB 저장값은 `USER/ADMIN`, `ACTIVE/DISABLED`다. API 값과 DB 값을 구분해서 기술한다.
- **추가 결정:** 이메일·계정·세션 수집 목적, 보관·삭제 시점, 만료 세션 정리 주기, 탈퇴 및 백업 내 데이터 처리. FK 삭제 설정은 회원 탈퇴 기능 구현 완료를 의미하지 않는다.
- **유지할 원칙:** 계정 도입이 검사 원문·결과·퀴즈 제출의 자동 저장을 허용하지는 않는다.
- **반영 대상:** 01 저장 범위, 03 데이터 저장, 04 테이블·보관 정책, 07 DB·개인정보

### GAP-005 공통 응답·오류·요청 ID 정합성

- **유형 / 우선순위 / 상태:** 문서·구현 불일치 / P0 / 미반영
- **문서 기준:** 05는 성공 `{request_id, data}`, 실패 `{request_id, error}`와 구조화 오류를 사용하고 BE가 UUID를 생성해 본문·헤더에 동일하게 반환한다.
- **근거:** 앱의 `request_id_middleware`, 인증 스키마 및 라우터, [health](../../KNUT-Capstone-Design-BE/app/api/routes/health.py)
- **현재 차이:** 응답은 envelope 없이 반환된다. 오류는 `HTTPException.detail` 및 기본 검증 오류 구조이며 공통 예외 변환기가 없다. 요청 ID는 헤더에만 있고, 입력 `X-Request-ID`가 있으면 UUID 검증 없이 그대로 사용한다. no-store 처리는 인증 경로에만 적용한다.
- **권장 조치:** 우선 기존 공통 계약으로 구현을 맞출지 합의한다. 인증만 별도 형식을 쓰려면 예외임을 명시하고 FE 파서를 분리한다. 요청 ID 신뢰·생성 규칙과 처리되지 않은 500 응답의 헤더·오류 구조도 테스트한다.
- **추가 오류:** 미인증, 권한 부족, 중복 이메일, 세션 만료 등 인증 전용 code와 `field=email/password` 확장을 정의한다. 오류 응답에 입력 비밀번호나 토큰이 포함되지 않도록 검증한다.
- **반영 대상:** 05 공통 규칙·오류·타입, 06 오류 UI, 07 계약·보안 테스트

### GAP-006 health의 준비 상태 의미 통일

- **유형 / 우선순위 / 상태:** 문서·구현 불일치 / P1 / 미반영
- **문서 기준:** 05 §8은 규칙·QR 디코더 초기화, DB 연결·스키마 준비를 확인하고 `data.status=ok`, `api_version=v1`을 반환한다.
- **코드 확인:** health는 DB `SELECT 1`만 실행하고 `{"status":"ready","database":"ready"}`를 반환한다. DB 오류는 503이다. 규칙·QR·스키마 준비는 검사하지 않는다.
- **필요한 조치:** 현재 endpoint를 DB 연결 확인으로 명확히 기술하고, 서비스 readiness 완료 조건을 별도로 관리한다. DB 연결 성공만으로 테이블이나 핵심 분석 기능이 준비됐다고 표시하지 않는다.
- **반영 대상:** 03 운영, 05 health, 07 상태·장애 테스트

### GAP-007 인증 요청 제한과 프록시 신뢰 범위

- **유형 / 우선순위 / 상태:** 문서 누락·추가 결정 필요 / P1 / 결정 필요
- **근거:** [요청 제한](../../KNUT-Capstone-Design-BE/app/core/rate_limit.py), [Dockerfile](../../KNUT-Capstone-Design-BE/Dockerfile)
- **현재 구현:** IP별 가입 5회/60초, 일반·관리자 로그인 합산 10회/60초. refresh/logout에는 해당 제한이 없다. 429에 Retry-After를 반환한다.
- **알고리즘:** 클래스 이름은 `FixedWindowLimiter`지만 실제로는 최근 60초의 timestamp를 유지하는 슬라이딩 윈도다. 상태는 프로세스 메모리에만 있어 worker 간 공유되지 않고 재시작하면 초기화된다.
- **구분할 점:** 05의 분석 20회·교육/퀴즈 60회 고정 구간 제한과 인증 제한은 서로 다른 정책이다. 기존 수치를 인증 수치로 일괄 치환하지 않는다.
- **프록시:** 컨테이너는 `--forwarded-allow-ips "*"`로 실행한다. 문서는 신뢰한 프록시의 헤더만 사용하도록 한다. host loopback 바인딩과 별개로 컨테이너 접근 경로·프록시의 전달 헤더 정리 설정을 확인하고 신뢰 대상을 제한해야 한다.
- **반영 대상:** 03 배포·보안, 05 요청 제한·인증, 07 제한·프록시 검증

### GAP-008 운영 DB 권한과 배포 절차 구체화

- **유형 / 우선순위 / 상태:** 문서·구현 불일치 / P0 / 결정 필요
- **문서 기준:** 04는 앱 SELECT 권한, 마이그레이션·seed 별도 계정을 요구한다.
- **근거:** [Compose](../../KNUT-Capstone-Design-BE/compose.yaml), Dockerfile, 설정, [환경 예제](../../KNUT-Capstone-Design-BE/.env.example), [BE 안내](../../KNUT-Capstone-Design-BE/README.md)
- **현재 구현:** 인증은 사용자·세션 INSERT/UPDATE가 필요하다. Compose는 DB 초기화 사용자와 migrate·api 접속 계정에 같은 설정을 사용한다. 앱·마이그레이션 계정 분리가 없다.
- **권장 조치:** 인증 테이블에 필요한 최소 쓰기 권한과 교육 테이블 조회 권한을 명시하고 앱 계정을 DB 초기화·스키마 변경 계정과 분리한다. SELECT-only 문구를 단순히 전체 쓰기 허용으로 바꾸지 않는다.
- **배포에 추가할 사실:** PostgreSQL `17.7-bookworm`, Python `3.12.12-slim`, SQLAlchemy·Alembic 사용. DB 포트는 host에 공개하지 않고 API는 `127.0.0.1:8000`에 바인딩한다. DB healthy → 일회성 migrate 성공 → API 시작 순서다. HTTPS 역방향 프록시는 Compose 외부에 필요하다.
- **환경 주의:** Compose 기본값은 production/Secure=true지만 `.env.example`은 development/Secure=false다. 예제를 복사만 해서 운영 설정이 완성되지는 않는다. production일 때 JWT 비밀값과 Secure 검증은 있으나 모든 배포 보안 조건을 검증하지는 않는다.
- **로컬 절차:** 예제 DATABASE_URL의 `db`는 Compose 서비스 이름이다. host에서 실행하는 로컬 절차에는 접속 가능한 PostgreSQL 주소 또는 개발용 SQLite 사용법을 구분해 적어야 한다.
- **미확인 운영 항목:** 실제 OCI 배포, TLS·도메인, 백업/복원, seed, 비밀값 관리·교체, 마이그레이션 실패 복구. 소스 설정만으로 완료 처리하지 않는다.
- **반영 대상:** 03 스택·배포, 04 계정·마이그레이션·백업, 07 운영 검증

### GAP-009 서비스 관리자와 기관 관리자 구분

- **유형 / 우선순위 / 상태:** 문서 누락·추가 결정 필요 / P1 / 결정 필요
- **근거:** 권한 의존성, User 모델, [관리자 생성 스크립트](../../KNUT-Capstone-Design-BE/scripts/create_admin.py)
- **현재 구현:** 역할은 user/admin 두 종류이며 기관 소속 모델이 없다. 관리자 전용 API는 내 정보 확인뿐이고 콘텐츠 관리 API는 없다. 일반 가입에서 역할을 지정할 수 없다.
- **운영 동작:** 스크립트는 새 관리자 생성뿐 아니라 기존 이메일 계정의 비밀번호 변경, 관리자 승격, 활성 상태 전환도 수행한다.
- **추가 결정:** 코드의 admin은 서비스 운영 관리자로 명명하고 기관 관리자와 분리한다. 관리자 생성·승격 승인, 비밀번호 재설정, 권한 회수, 기존 세션 처리 및 감사 기록 정책을 정의한다. 일반 로그인 endpoint를 관리자가 이용할 수 있는지도 현재 동작과 함께 명시한다.
- **반영 대상:** 01 역할, 02·06 관리자 흐름, 04 권한 모델, 05 권한 계약, 07 권한 테스트

### GAP-010 테스트 계획에 인증 검증과 PostgreSQL 실행 증거 추가

- **유형 / 우선순위 / 상태:** 문서 누락·문서·구현 불일치 / P1 / 미반영
- **근거:** [인증 테스트](../../KNUT-Capstone-Design-BE/tests/test_auth.py), [health 테스트](../../KNUT-Capstone-Design-BE/tests/test_health.py), [fixture](../../KNUT-Capstone-Design-BE/tests/conftest.py)
- **존재하는 테스트:** 가입→내 정보→갱신→로그아웃, 중복 가입·약한 비밀번호, 잘못된 로그인·없는 계정의 동일 오류, 관리자 로그인·권한 분리, 비활성 계정 로그인 차단, 인증 no-store·요청 ID, 가입 제한, health 성공.
- **증거의 한계:** 테스트 함수가 있다는 사실만 확인했다. 이번 검토에서 실행하지 않았다. 정상 일반 로그인 성공을 직접 검증하는 별도 assertion은 없고, 함수명에 login이 들어간 통합 흐름도 가입 후 받은 토큰을 사용한다.
- **DB 차이:** fixture는 인메모리 SQLite와 `metadata.create_all()`을 사용한다. PostgreSQL에서 Alembic을 실행하는 통합 검증을 대체하지 못한다.
- **추가할 시나리오:**
  - 정상 일반 로그인, 입력 길이 경계, 추가 필드·역할 주입 차단.
  - 토큰 누락·변조·만료, 비활성 계정의 기존 access/refresh 거부.
  - refresh 순차 재사용·동시 갱신·만료, 로그아웃 후 access token의 합의된 동작.
  - 실제 브라우저의 Secure/SameSite/CORS/credentials 및 CSRF 정책 검증.
  - 로그인 제한 공유·시간 경계·재시작·다중 worker와 신뢰 프록시 검증.
  - 오류에 비밀번호·토큰 미노출, 공통 envelope·요청 ID·캐시 계약.
  - 독립 PostgreSQL에서 빈 DB 마이그레이션, 유일 제약·FK·트랜잭션, DB 장애, 계정 권한 분리.
- **반영 대상:** 07에 인증 테스트 ID와 기대 결과 추가. 기존 MVP 인수 조건과 인증 선행 개발 결과는 분리한다.

### GAP-011 핵심 기능 미구현을 문서 누락과 분리

- **유형 / 우선순위 / 상태:** 설계 대비 미구현 / P1 / 미반영
- **근거:** 앱 라우터 등록, 모델 목록 및 첫 마이그레이션. BE README의 공개 분석·교육 설명은 해당 API 구현 존재의 근거가 아니다.
- **현재 확인되지 않은 구현:** URL·문자·QR 분석, 위험도·근거 계산, 교육 사례 조회, 퀴즈 조회·채점, 교육·퀴즈 스키마 및 seed. AI 생성·조작 이미지 탐지 endpoint도 없다.
- **문서 처리:** 미구현이라는 이유로 01~07의 요구사항을 삭제하지 않는다. 기능별 진행 현황과 구현 PR·테스트 증거를 연결하고 완료 전까지 계획으로 표시한다.
- **추가 구분:** 임찬우 담당 AI 생성·조작 이미지 탐지와 스미싱 규칙 기반 분석은 서로 다른 작업이다. AI 기능의 착수 범위 변경이 필요하면 별도 요구사항 합의와 API 설계를 기록한다. 인증 코드에서 AI 연동 계약을 추정하지 않는다.
- **반영 대상:** README 진행 현황, 01 범위·우선순위, 03 모듈, 04·05·07 구현 추적
